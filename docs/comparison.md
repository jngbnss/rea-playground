# 원본 vs 재구현 데모 비교

- 원본: <https://jngbnss.github.io/f1/?car=f1-ferrari&track=melbourne&ai=0&laps=3>
- 데모: `experiments/f1-recreation` (`npm run build` → `vite preview`, `http://localhost:4173`)
- 측정일: 2026-10-14
- 측정 방법: 두 페이지 모두 **같은 Chrome 155**(임시 프로필, CDP 9222)에서,
  `Input.dispatchKeyEvent`로 `rawKeyDown`을 보내 키를 **누른 상태로 유지**하고
  HUD 속도계 텍스트를 약 100 ms 간격으로 읽었다.
- 원자료: `docs/evidence/throttle-run-original-clean.csv`, `throttle-run-demo.csv`, `brake-runs.csv`

> 주의 1: 이 측정은 **REA 분석 결과가 아니라 자체 계측**이다.
> 주의 2: 샘플 간격이 ~105 ms이므로 시간 수치의 분해능은 ±1 샘플(≈0.1초)이다.
> 주의 3: 각 항목 1회 주행만 측정했다. 분산은 알 수 없다.
> 주의 4: 배경 탭은 Chrome이 rAF를 억제한다. 측정 전 반드시 `Page.bringToFront`로
> 대상 탭을 전면에 두었다(그렇지 않으면 FPS가 2까지 떨어진다 — `errors.md` E-011).

## 1. 가속 (W 유지, 정지 → 최대)

| 구간 | 원본 | 데모 | 차이 |
| --- | ---: | ---: | ---: |
| 0 → 100 km/h | 2.78 s | 2.34 s | 데모가 0.44 s 빠름 |
| 0 → 200 km/h | 5.22 s | 4.98 s | 데모가 0.24 s 빠름 |
| 0 → 250 km/h | 6.59 s | 6.71 s | 데모가 0.12 s 느림 |
| 7.0 s 시점 최고 | 256 km/h | 257 km/h | 거의 동일 |

**해석**

- **곡선 모양이 같다.** 저속에서 가파르고 고속으로 갈수록 완만해지는, `min(engineForce, P/v)`
  구조 특유의 형태가 양쪽 모두에서 나타난다. 250 km/h 부근에서 두 곡선이 교차한다.
- **저속 구간에서 데모가 더 빠른 이유** — 원본은 네 바퀴가 각각 레이캐스트 서스펜션으로
  하중을 받고, 그 하중에 비례한 그립 한계 안에서만 구동력이 노면에 전달된다.
  발진 시 하중 이동·휠스핀으로 실제 전달력이 `engineForce`보다 작다.
  데모는 자전거 모델이라 하중 이동이 없고, 접지 한계를 `μ·normalLoad` 하나로만 클램프한다.
- **고속에서 역전되는 이유** — 데모의 `dragCoefficient = 0.9`(자체 설계값)가 원본보다 크게 잡혀
  고속에서 저항이 더 빨리 커진다. 원본의 실제 계수는 차종 테이블에 있고 **[미확인]**이다.

## 2. 제동 (약 186 km/h에서 S 유지)

| 항목 | 원본 | 데모 |
| --- | ---: | ---: |
| 시작 속도 | 186 km/h | 187 km/h |
| 정지까지 | **2.10 s** | **2.62 s** |
| 평균 감속도 | ≈ 2.46 g | ≈ 1.98 g |

**해석** — 데모가 약 25 % 느리게 선다.

1. 원본은 제동력을 `brakeBias`로 앞/뒤에 나눈 뒤 **바퀴별 수직하중 기준 그립 한계**와 비교하고,
   초과하면 휠 락 처리까지 한다. 제동 중 앞쪽으로 하중이 이동해 앞 타이어가 더 큰 힘을 낸다.
2. 데모는 하중 이동이 없어 앞뒤 하중이 정적 배분 그대로다. 또 `brakeForce = m·g·4` **[분석확인]**를
   그대로 쓰면 μ=1.6 한계를 넘기 때문에 `μ·normalLoad`로 클램프했고(**[자체설계]**),
   그 결과 저속 구간에서 제동력이 원본보다 작아진다.
3. 두 경우 모두 **브레이크 압력 램프(상승 10/s)** 가 적용되어 처음 0.1초는 제동력이 차오른다.
   데모 첫 샘플에서 속도가 오히려 189 km/h로 살짝 오른 것이 그 구간이다.

## 3. 조향 반응

| 항목 | 원본 | 데모 |
| --- | --- | --- |
| 조향 즉시성 | 슬루율 제한 (꺾기 6.46/s, 복귀 8.12/s) | **동일 수식·동일 상수** |
| 고속 조향각 축소 | `maxSteerLowSpeed + (maxSteerHighSpeed·1.35 − low)·n(2−n)` | **동일 수식** |
| 측정된 고속 포화 조향각 | **[미확인]** (내부 값 접근 불가) | **0.162 rad** (= 0.12 × 1.35) |
| 107 km/h 시점 조향각 | **[미확인]** | 0.1754 rad |
| 정상 선회 요레이트 | **[미확인]** | 좌 +0.47 rad/s, 우 −0.50 rad/s |

**해석**

- 데모에서 측정한 포화 조향각 0.162 rad는 분석에서 도출한 식
  `maxSteerHighSpeed × highSpeedLock = 0.12 × 1.35`와 **정확히 일치**한다.
  → 조향 수식 재현이 의도대로 동작함을 수치로 확인했다.
- 원본의 조향각 실수치는 HUD에 노출되지 않고 번들 내부 변수로만 존재해 **비교 불가**다.
  `maxSteerLowSpeed / HighSpeed / FadeSpeed` 자체가 **[미확인]**이므로,
  "체감이 비슷한가"는 주관 평가일 뿐 수치 비교가 아니다.

## 6. 입력 지연

| 측정 | 원본 | 데모 |
| --- | --- | --- |
| `keydown` → 속도 > 0 (3회) | 89 / 27 / 29 ms | 28 / 49 / 29 ms |

**해석** — 두 값 모두 **CDP 왕복 시간(약 15–25 ms)을 포함한 상한값**이며 유의미한 차이가 없다.
원본 첫 회 89 ms는 측정 직전 리셋 직후 프레임이라 **이상치로 본다**.
실제 입력 지연은 두 구현 모두 `window` 리스너 → 다음 fixedUpdate(최대 16.7 ms) 구조로 동일하다.

## 9. 결론

- **입력 처리 → 명령 변환 → 카메라 → HUD** 계층은 분석에서 확인한 수식을 그대로 옮겼고,
  고속 포화 조향각 0.162 rad처럼 **예측값과 실측값이 일치**하는 지점에서 재현을 확인했다.
- **차량 동역학 계층**은 근사(자전거 모델)이므로 가속 곡선은 비슷하지만 제동은 25 % 차이가 난다.
  이 차이의 원인은 "하중 이동과 바퀴별 그립 한계의 부재"로 설명되며, 추측이 아니라
  두 구현의 코드 구조 차이에서 직접 따라 나온다.
- 즉 **느낌이 비슷한 부분은 수식을 공유해서이고, 다른 부분은 모델 차원이 달라서다.**
